# AGENTARIUM

## dsh 工作流可视化插件｜产品需求文档（PRD）

**版本：** V1.0（方案定稿候选）  
**日期：** 2026-10-18  
**产品形态：** DeepSeek Harness（dsh）客户端插件  
**落点：** 对话页顶部视图切换中的第三个 Tab——「工作流」  
**设计主题：** 无图片素材的 ASCII 智能体基地 / 任务指挥室  
**优先平台：** dsh Desktop，兼容共享 Web Client  
**文档定位：** 产品体验、世界建模、视觉方案、范围与验收；不代替详细工程设计

> **一句话定义**：把 Agent、Subagent、工具调用与工作流的真实执行事件投影为一个可以观察、定位、回放的 ASCII 游戏世界；让用户像指挥一个小型远征队一样理解复杂任务，但不牺牲执行事实的准确性。

# 01. 执行摘要与明确结论

### 1.1 本次决定

1. **入口不另开 Sidebar**：在现有「对话（order 0）」「轨迹（order 10）」后新增 **「工作流（建议 order 20）」**，通过 dsh 的 `conversation.view` 插件扩展点注册。默认打开仍是「对话」；用户主动选择「工作流」后按照原有视图偏好机制恢复。
2. **表现形式选择**：首版采用「**ASCII 任务基地 + 轻量指挥盘**」，不是完整 3D 游戏，也不是传统可拖拽 DAG 编辑器。场景负责空间感，事件流和检查器负责业务准确性。
3. **动画与素材策略**：采用 **ascii.rest + 自研轻量事件场景模型 + React HTML 交互层**。无预制 PNG、角色立绘、Spine、Lottie 或 3D 模型需求；但仍须编写字符图形规则、角色姿态与场景布局代码。
4. **MVP 聚焦“可观察”**：一个会话的主 Agent、可见子 Agent、工具事件、状态/错误、点击详情、历史加载和简化动画。**不在首版修改模型工作流程、自动决定任务进度或绕过 dsh 权限。**
5. **价值衡量**：不是观看时长或动画数，而是用户能否更快回答“谁在做什么、哪里阻塞、为什么失败、产物在哪里”。

### 1.2 可行性结论

| 议题 | 结论 | 说明 |
| --- | --- | --- |
| 与「对话 / 轨迹」并列新增 Tab | **已由源码确认** | `conversation.view` 是列表 Slot；Chat 和 Trajectory 分别注册 `id`、`order` 与视图组件。 |
| Electron Desktop 中运行 | **可行** | Desktop 复用 Web Client；不需要新原生窗口，也不需要修改 Electron 壳。 |
| ascii.rest 用于动画 | **可行** | React 组件、自定义 `piece()` 绘制、分层、移动、粒子和图表可直接使用。 |
| ascii.rest 直接当完整游戏引擎 | **不建议** | 它不提供 Agent 语义、任务关系、寻路、命中区、回放时间轴与权限控制。 |
| 完全不制作图片素材 | **可行，需取舍** | 无需美术贴图，但需要字符角色/建筑模板、布局、色彩和状态动画的设计工作。 |
| 精确展示所有 Subagent 内部动作 | **不能保证** | 本地可读子会话与外部执行可见性不同；不可见部分必须标注“未知/外部”。 |

### 1.3 非目标

首版不承诺可视化编辑工作流脚本、不操纵任意其他会话、不预测剩余时长、不根据工具数量计算任务完成百分比、不生成未经确认的依赖关系，也不把用户任务变成鼓励无意义调用的积分游戏。

# 02. 问题、机会和用户价值

### 2.1 用户问题

dsh 已有 Chat、Trajectory、Subagent 列表、Workflow 层级和后台任务监控，但信息位于不同视图。用户面对复杂任务时会出现四种摩擦：

- **信息分散**：需要在对话、轨迹和子任务之间反复切换，才能建立全局认知。
- **并行不直观**：连续文本不擅长表达多个 Agent 同时工作、结果回传和等待关系。
- **异常不突出**：大量正常调用淹没失败、重试、审批和长期等待等真正重要的节点。
- **复盘成本高**：历史轨迹信息完整，但还缺少一眼看懂的“这段执行发生了什么”的空间故事。

### 2.2 用户角色与 JTBD

| 用户 | 场景 | 真正要完成的工作 |
| --- | --- | --- |
| Agent 重度使用者 | 运行多个 Subagent 审查大型项目 | 快速定位运行者、异常者、等待者与最终交付物 |
| 普通开发者 | 让 dsh 帮忙改代码、测试、生成报告 | 不必读大量工具日志，就能判断任务进展和风险 |
| AI 产品研究者 | 比较提示词、工作流和执行策略 | 复盘何时委派、重试、失败、恢复及其代价 |
| 教学 / 演示用户 | 向别人展示多 Agent 工作方式 | 用有趣但不失真的方式解释 Agent 执行 |

**核心 JTBD：** 当我把任务交给 dsh 时，我希望以低认知成本看见真实执行的组织结构，并能在发现问题时直接进入可信的原始上下文，从而决定是等待、检查还是介入。

### 2.3 体验承诺

第一眼知道谁在工作；第二眼发现哪里需要注意；第三步点进去可以看到真实证据。趣味性服务于理解，不反过来替代事实。

# 03. 产品定位与核心循环

**中文 Tab 名称：** 工作流  
**内部产品名：** Agentarium  
**界面子标题：** 智能体基地  
**首版世界观：** 多个 AI 队员在一个“终端基地”内执行远征任务。建筑代表工具能力，队员代表 Agent 或 Subagent，行动代表执行事件，成果仓库代表已经识别的交付物。

**项目世界设定（2026-10-18 补充）：** 终端基地是默认世界。用户可以让模型结合不同项目生成或修改 `.agentarium/world.json`，定制背景故事、队伍名称、角色称谓、设施名称和装饰强调色。同一项目的会话复用设定，执行事实仍按会话隔离。具体保存、修改、刷新、回放和验收约定见[按项目定制远征队世界设定](WORLD-SETTING.md)。该补充更新了首版可配置范围，复杂图形主题仍属于后续扩展。

### 3.1 三层体验

1. **观战（Observe）**：角色、行动、工作阶段、需要注意的事件。
2. **调查（Inspect）**：点击角色/建筑/事件，查看准确时间、调用身份、参数摘要、结果、状态和原生详情跳转。
3. **复盘（Replay）**：根据真实记录重建某一时点世界状态，暂停/快进/选中异常节点。首版可仅支持历史定位，完整可控回放安排在 V1。

### 3.2 长期产品循环

`发起任务 → 自动生成基地状态 → 观察并行执行 → 捕捉异常 → 进入详情/原生操作 → 获取产物 → 保存复盘视角`

游戏化的“奖励”优先表现为完成事实与可用产物，而不是无意义经验值。一个工具成功返回不等于整项任务完成。

# 04. 入口、布局与导航规范

### 4.1 入口及与既有 Tab 的关系

固定放置在对话主视图的视图切换区：

`[ 对话 ]  [ 轨迹 ]  [ 工作流 ]`

它属于 `conversation.view`，**不属于**右侧文件预览 / Browser / Terminal 的 `sidebar.right.pane.tab`。从工作流点击某个 Agent 的具体原始记录，可以导航到原生 Trajectory，或在 dsh 已支持的场景下打开对应子会话；需要看文件则继续使用原有 Sidebar。

默认选中仍是「对话」。安装插件不会抢焦点，不改变已有会话输入框、停止按钮或工具审批流程；卸载后视图自然消失，回落到原生默认视图。

### 4.2 主视图信息架构

**A. 顶部状态带（固定高度）**：任务标题、运行态、可见 Agent 数、正在执行的工具、失败/待处理事件数量、切换“实时/历史”。不展示无法证明的百分比。

**B. 中央 ASCII 场景（主要空间）**：基地建筑、Agent 角色、可见的工具行为、子 Agent 生成与结果回传。点击元素进入检查器。

**C. 底部事件队列（可折叠）**：按时间排序的关键事件摘要；支持异常筛选、选中后联动场景。

**D. 检查器（按需）**：宽屏在场景内右侧抽屉展示；窄屏使用底部抽屉。检查器只展示已记录的事实，复杂参数和日志跳转至原生 Trajectory。

**E. 轻量工具栏**：聚焦当前活动、降低动效、视图缩放、重新排列建筑；历史版再增加时间轴。

### 4.3 ASCII 线框草图（概念，非截图）

```text
Session: Review repository     [对话] [轨迹] [工作流*]
+--------------------------------------------------------------+
| LIVE  Agents 3  Calls 7  Errors 1  Waiting 0    [History]    |
+---------------------------------------------+----------------+
|  +---------+        A1 . . . > +----------+ | ACTION DETAIL  |
|  | ARCHIVE |                   | TERMINAL | | Agent: A1      |
|  |  READ   |       A0          |   RUN    | | Tool: bash     |
|  +---------+                   +----------+ | State: running |
|        ^                                   | | [See in Trace] |
|       A2         +----------+             | +----------------+
|                  |  TEST    |             |
|                  |   OK     |             |
|                  +----------+             |
|  [ HQ ] ---[ portal ]---[ output depot ]  |
+---------------------------------------------+----------------+
| 13:21 A2  read_file completed                                   |
| 13:22 A1  bash started                                          |
| 13:23 A0  subagent result received                              |
+----------------------------------------------------------------+
```

说明：`A0/A1/A2` 是稳定且可识别的角色短标签，中文字用于 HTML 信息层，**不强行塞进等宽 ASCII 网格**，以避免字符宽度和排版问题。

### 4.4 响应式策略

- **宽屏（建议可用宽度 ≥ 960px）**：场景与检查器并排，信息层常驻。
- **中屏（约 600–959px）**：场景完整宽度；检查器为浮层，事件列表收起。
- **窄屏（约 < 600px）**：自动转成“紧凑 ASCII 战术地图 + 事件卡片”；角色不强制走位，仅闪烁状态；减少标签密度。
- **高度不足或窗口拆分**：优先保证关键事件与点击目标可用，装饰性场景自适应裁剪，不允许隐藏报警。

以上断点是设计初值，最终应以 dsh 实际容器尺寸原型测试调整，而非当作既有框架限制。

# 05. MAGIC 世界模型（产品领域模型）

使用 **MAGIC = Mission / Agent / Game Action / Impact / Choice** 五层模型，将真实执行事实映射为可理解的世界状态。

| 层 | 对象 | 说明 | 不应误解为 |
| --- | --- | --- | --- |
| M / Mission | 一次会话、轮次或显式 Workflow 运行 | 任务目标、可见阶段、开始/结束情况 | 模型必然有完整规划 |
| A / Agent | 主 Agent、本地子 Agent、外部任务占位 | 角色身份、父子关系、真实可观察状态 | 外部任务内部状态可被读取 |
| G / Game Action | 工具调用、模型步骤、委派、后台作业 | 某主体在某时间做了何事 | 相邻事件必然有依赖关系 |
| I / Impact | 工具结果、错误、真实文件/报告/测试结果 | 有证据支撑的局部结果和最终交付 | 工具成功 = 用户目标成功 |
| C / Choice | 用户审批、停止、指导、跳转调查 | 用户真实可执行的决策 | 自制 UI 可以绕过原有权限 |

### 5.1 主要对象

**World（基地）**：绑定当前会话和时间游标；保存视图布局和当前选择，不掌握 Agent 真相。  
**Mission（远征任务）**：用户发起的会话活动；显式 Workflow 作为 Mission 内的结构化行动块。  
**Actor（队员）**：按已知 Agent 身份构建；`root` / `local-subagent` / `external` 三种可见性级别。  
**Facility（设施）**：按工具类别分组的视觉节点，并非真实执行系统里的资源；同一类别可有多次行动。  
**Action（行动）**：带稳定调用身份的工具执行及其可追溯状态。  
**Evidence（证据）**：可对应 Session 记录、工具结果、报告或可访问的子 Session。  
**Relation（关系）**：仅允许“明确委派/属于工作流成员/同一调用内部子调用/结果回传/时间邻接”等带类型来源的关系。  
**Choice（用户操作）**：始终经 dsh 原生服务执行，游戏界面只是安全入口。

### 5.2 事实分级（必须可见）

- **F0 已记录事实**：持久 Session 事件、可确认的工具结果/子会话关联、明确的 Workflow 阶段。
- **F1 当前已观察状态**：实时运行中、等待批准、动态输出等；失联后可降级为“状态未知”。
- **F2 视觉推演**：角色从 HQ 走到 ARCHIVE、抖动、光效、烟雾、路径选择；只用于呈现，不得回写为事实。

产品中的执行事实文案、百分比与功能按钮只能来自 F0/F1；F2 不得解释为 Agent 的真实思考或实际物理行动。独立标识的世界背景、角色称谓和设施显示名可来自项目设定，不得覆盖事实摘要与状态。

### 5.3 状态机定义

| 事件事实 | 世界状态 | 默认视觉表现 | 用户下一步 |
| --- | --- | --- | --- |
| 会话开始 / 轮次开始 | Mission 活跃 | HQ 点亮、角色进入基地 | 看实时概览 |
| 工具调用已发起 | Action running | 角色前往对应设施；设施显示忙碌 | 点选工具详情 |
| 工具成功结算 | Action succeeded | 设施短暂高亮，结果进事件队列 | 查看结果/输出 |
| 工具失败结算 | Action failed | 设施短红提示，异常计数增加 | 一键定位原始记录 |
| 子 Agent 创建/委派 | Actor spawned | 生成一个带身份标签的小人 | 查看其任务/子会话 |
| 子 Agent 完成 | Actor idle/settled | 角色返回 HQ 或退场，保留回传记录 | 查看结果 |
| 明确审批等待 | Attention required | 行动暂停、出现“需要决定”旗标 | 跳转原生审批 |
| 工作流阶段开始/完成 | Phase active/done | 阶段旗帜更新；显式阶段显示关联 | 查看成员关系 |
| 会话失联/重连中 | Unknown/reconnecting | 冻结当下画面 + 明确状态层 | 等待恢复或重新载入 |
| 正常轮次结束 | Turn ended | HQ 安静、结束摘要 | 进入复盘 |
| 取消/中断 | Cancelled/interrupted | 不播放成功庆典，显示实际原因 | 检查中断原因 |

**关键约束**：没有明确 `end` 的长任务，不可以在模型 `step/end` 时擅自宣告任务结束；后台作业可能在工具 Step 之后继续运行。`unknown` 与 `failed` 必须分开。

### 5.4 Agent 角色标识

角色 ID 使用现有可得的稳定身份确定，显示名使用短标签 `A0`、`A1`、`A2`，按已知会话父子关系排列。角色外观可由稳定 ID 派生颜色/帽子/轮廓，刷新后保持一致；**不允许随机更换身份**。外部 Subagent 只显示“远程队员 / 内部不可见”，避免制造错误的执行细节。

# 06. ASCII 世界的视觉与动画建模

### 6.1 视觉方向：Terminal Colony

采用终端风格的 2D 基地，而非高帧率像素动作游戏。视觉关键词：轻复古、清楚、微妙、结构化、有趣但安静。场景由字符地图、简单角色、设施轮廓、少量色彩及环境效果组成；文本详情仍由正常 HTML 字体呈现。

**为什么不是复杂 RPG**：角色打斗、升级和移动过多会把执行过程解释成主观故事；而工具调用与会话事实上更像“工坊与指挥室”的协作。

### 6.2 建筑语义映射

| 实际类别 | 设施名称 | 字符形象（概念） | 触发场景 |
| --- | --- | --- | --- |
| read / file / search | 档案馆 ARCHIVE | 书架、`[==]`、文件条 | 读取与检索 |
| write / edit / diff | 制造工坊 WORKSHOP | `[##]`、锤击光点 | 文件编辑与变更 |
| shell / terminal / bash | 控制台 TERMINAL | `>_` 提示符、输出波纹 | 命令和脚本执行 |
| tests / verification | 试炼场 TEST | `OK/ERR` 灯、测试管线 | 识别到测试执行时 |
| browser / web / fetch | 瞭望台 WEB | 雷达圆圈、扫描线 | 访问网页与搜索 |
| subagent / workflow | 传送门 PORTAL | `(@)`、出现/离开效果 | Agent 委派和流程编排 |
| 其他 / 未归类工具 | 通用站 UTILITY | `[*]` | 安全降级 |
| 明确交付文件或结果 | 成果仓库 DEPOT | 文件卡、登记条 | 结果被用户/系统确认可访问 |

“测试设施”不是所有 bash 命令都去的地方：只有在工具元数据、明确命令上下文或已记录结果能够识别为测试时才用；无法判断的终端命令仍归入 TERMINAL。

### 6.3 角色最小动作集

- **Idle**：轻微呼吸（字符形态在两帧中切换）或固定姿态。
- **Move**：沿短路径 3–5 步移动，单次约 400–900 毫秒；立即转场不会改变真实开始时间。
- **Work**：设施符号周期变化，例如 `>_` / `>.` / `>>`；不持续重新绘制大量文字。
- **Complete**：成功光点 0.3–0.6 秒，仅标记行动结算。
- **Error**：短暂抖动/反色 + 持久错误徽标；不以爆炸特效遮盖失败。
- **Spawn**：Portal 出现另一角色与名称标签；只在已证实子项创建时触发。
- **Wait**：状态旗标常驻，动效趋于静止；不会自动判定卡死。
- **Return**：收到结果的子 Agent 退回 HQ 或保持 Idle，具体取决于是否仍活跃。

角色行为动作**不能反推**真实步骤或消耗 token；动画时长与工具真实耗时解耦。

### 6.4 ASCII 与 UI 文字分工

- ASCII 网格：背景、角色轮廓、设施、移动、粒子、装饰；优先安全的半角字符。
- HTML/CSS：中文标签、精确时间、数值、参数预览、按钮、可读提示、焦点框和无障碍信息。
- 业务叙述：工具名称和结果应保持原始可点击来源；游戏名称不能取代真实标识。

# 07. ascii.rest 专项可行性与取舍分析

### 7.1 它实际是什么

`ascii.rest` 是 MIT 授权的动画 ASCII Art 库，支持 `ascii.rest/react`、`ascii.rest/kit`、`mount()`、自定义 `piece()` 和 `Surface` 字符网格。内置大量独立动画，既有 `<pre>` 文本绘制，也有 `<canvas>` 彩色绘制。它提供帧率、时间驱动帧、图层/网格布局和 reduced-motion 支持；npm 打包时可以离线使用。资料见末尾来源。

### 7.2 对本产品的能力匹配

| 需求 | ascii.rest 能否满足 | 适用方式 | 风险 |
| --- | --- | --- | --- |
| 字符角色和建筑 | **能** | `piece()` 绘图、Surface `set/write/paste` | 仍需定义美术造型规则 |
| 简单移动/闪烁/粒子 | **能** | 时间 `t`、kit Motion/Effects/Particles | 要同步外部事件开始时间 |
| 一整幅终端场景 | **基本能** | 单场景 piece 或自定义字符网格 | 频繁实时状态变化要测试更新策略 |
| 多层场景合成 | **能** | `layer/over/grid`、自定义 Surface | 图层事件与视觉优先级需自己管 |
| Agent 状态和工具生命周期 | **不能直接** | 自己的真实事件世界模型提供状态 | 不应让动画猜测事实 |
| 点击任意角色/建筑 | **非内置游戏命中系统** | React 透明交互覆盖层或场景坐标映射 | 响应式缩放和精确点击需实现 |
| 自动寻路与碰撞 | **不是现成能力** | 自研简易栅格位置与路径动画 | MVP 应避免复杂导航 |
| 复盘控制和跳转原生详情 | **不能直接** | 使用 dsh 事件、时间轴和 UI 导航 | 保证重连/历史一致性 |
| 离线桌面客户端 | **能** | npm 依赖参与客户端 bundle | 不使用远程 script / CDN 字体 |
| 无障碍 / 减少动效 | **基本支持** | `label`、`prefers-reduced-motion`、fps 0 | 交互必须另有可访问 DOM |

### 7.3 推荐集成方式（正式建议）

**业务模型 → 场景状态 → ASCII 渲染 + React 交互覆盖层**：

```text
真实 Session / Workflow / Subagent / Tool 事件
                     |
             事件归一与证据绑定
                     |
             Agentarium World State
                     |
       +-------------+--------------+
       |                            |
 ASCII 场景绘制 / ascii.rest      React 控件与检查器
  (图形、运动、特效)              (点击、文字、跳转)
       |                            |
       +-------------+--------------+
                     |
              一个「工作流」Tab
```

ascii.rest 应用于视觉低层，不接触真实执行控制。动态世界的每个角色/行动位置由我们决定；库只负责把状态绘制得好看。

### 7.4 为什么不直接把所有东西做成 `<Ascii>` 动画组件

官方 React 文档明确说明：`<Ascii>` 的 options 发生变化时动画会从第一帧重新开始，新创建的 piece 也会重启。Agent 状态流有频繁局部更新，若每个 Agent 都用独立 `<Ascii>` 并重复构造，容易造成动作跳变、渲染和状态同步复杂化。因此首版优先**一个稳定场景绘制单元 + 细粒度状态层**，辅助动效才用独立 `<Ascii>` 组件。对“随事件瞬时改变画面且不中断时间连续性”的部分做专门原型验证。

### 7.5 运行限制和处理策略

- 自定义 `piece()` 官方当前上限为 **320×120 字符格**；首版场景远小于上限（例如 80×28 或 100×34）。
- 官方默认最高约 30 fps，也能以 12 fps 等较低速率绘制；首版建议日常 **12–15 fps**，高动效短时 **20–24 fps**，空闲静帧停止。
- 文本 piece 使用 `<pre>`，彩色 piece 使用 `<canvas>`；两种方式缩放逻辑不同。建议单一受控场景，按明确字体测量固定字符网格。
- 打包依赖而不是用 `https://ascii.rest/ascii.js` 远程脚本；字体如需补充也应随产品本地打包。
- `ascii.rest/kit` 需使用支持 kit 的版本（官方文档标注 0.4.0 及以上）；最终锁定版本、包大小与 dsh 构建兼容性仍需安装实测。
- 文本 art 自带屏幕阅读器 label 并不能替代角色/事件的语义列表；要有键盘可操作的 DOM 镜像。
- MIT 授权允许商用和修改，但发行产物保留版权和许可声明。

### 7.6 备选路线及触发条件

**首选：ascii.rest + 自研轻量 ASCII Scene。** 原因是最接近“零美术素材”、开发展示原型快、终端风格贴合 AI 工具。  
**备选 1：纯 CSS + DOM 字符格**。当需要大量独立可点击对象且性能更好时使用；缺点是角色动效较原始。  
**备选 2：纯 Canvas 2D + 字符绘制**。当场景需要高频动态更新或更高效命中映射时考虑；需自行承担渲染管线。  
**暂不考虑**：PixiJS / Phaser / Three.js 作为 MVP 主引擎——功能足但体积、概念和成本与我们的目标不成比例。

**原型决策门槛**：在真实 dsh Session 流上完成连续运行、回放/切换 Tab、30 分钟低功耗观察与 1000+ 事件历史加载后，再决定 ascii.rest 是否承担主场景渲染；未通过时保留世界模型，替换底层绘制方式即可。

# 09. 关键交互规范

### 9.1 进入工作流 Tab

**用户操作：** 点击「工作流」。  
**预期结果：** 如有活动立即呈现当前快照，随后响应实时事件；若是历史会话则显示可靠记录与数据范围。不能因为初始化图形而阻塞输入框或原始聊天能力。

### 9.2 点击 Agent

默认出现身份卡：名称/类型/状态、父级、已知任务标签、已记录工具调用数、可访问的子会话入口。**未知的外部任务不提供不存在的“内部轨迹”按钮**。再次点击聚焦同一角色；在空白区点击解除选择。

### 9.3 点击设施 / 工具动作

设施本身展示工具类别和当前活动数；点击具体行动才打开包含 callId、tool name、开始/结算时间、状态、参数摘要、结果摘要与“在轨迹中查看”的检查器。敏感参数默认折叠，长输出从原有原生详情读取。

### 9.4 点击事件列表

更新当前选择、场景高亮和检查器。若事件对应的记录不在当前历史窗口，提供“加载更早记录”动作；不可猜测详情。异常过滤不改变真实时间顺序。

### 9.5 实时与回放切换

“实时”代表当前最新可观察状态；“回放”代表基于已加载历史可定位时间点。进入回放时场景暂停在选中记录，但 Agent 真实执行不暂停。界面必须始终区分 **暂停播放** 与 **停止 Agent**。恢复实时后定位最新事件，历史游标可单独保存。

### 9.6 用户控制

P0 为只读观察与原生详情导航。P1 可以提供“打开审批”“停止子 Agent”等入口，但其可用性以 dsh 原生授权、会话关系和实时状态为准。所有危险操作必须使用现有确认机制；小游戏的视觉按钮没有独立权限。

# 10. 动画触发与优先级规则

### 10.1 事件到动作映射

| 优先级 | 触发 | 动画反馈 | 持续策略 |
| --- | --- | --- | --- |
| 最高 | 用户审批/严重失败/被中断 | 角色上方固定提示、对应设施标识 | 必须持续到已确认/用户处理 |
| 高 | subagent 创建/完成、Workflow 阶段结算 | Portal、团队关系线、阶段旗帜 | 一次性短动画 + 状态常驻 |
| 中 | tool/call 和 tool/result | 角色移动、设施忙碌/完成 | 短动作，重复事件节流 |
| 低 | token/stream 增量、普通日志 | 微弱终端扫描或不动画 | 合批、可关闭 |
| 背景 | 环境动效 | 雨/闪烁/呼吸 | 低帧率且不影响识读 |

### 10.2 高频事件处理

同一 Agent 在短时间内产生大量调用时，不允许出现几十个小人排队动画造成延迟。事实列表保持全量，场景只维持至多一个“当前主动作”和有限并发徽标；额外调用聚合为 `+N`。如绘制速度跟不上事实，优先**跳过装饰帧**，绝不丢失关键事件或延迟真实异常提示。

### 10.3 因果关系的视觉规则

**允许画实线**：持久化父子关系、显式 Workflow 成员、真实工具子调用。  
**允许画虚线**：严格标注为“同一时间段”或“最近活动”的非因果连接。  
**禁止画箭头**：仅因时间上 A 在 B 之前，就宣称 B 依赖 A；仅因文件名相似就声称结果被复用。

# 11. 典型用户旅程

### 11.1 场景 A：多 Agent 仓库审查

**用户任务：**“扫描项目架构、运行测试、给出改进报告。”

1. **T0**：进入工作流视图，HQ 出现主 Agent `A0`，状态是运行中。
2. **T1**：`A0` 创建两个已确认的本地子 Agent。Portal 出现 `A1`（检索）和 `A2`（测试）。若某项是外部执行，仅绘制“远程任务”占位。
3. **T2**：`A1` 调用 read/search；它移动到 ARCHIVE。`A2` 运行 bash；它去 TERMINAL。两个动作可同时处于忙碌态。
4. **T3**：测试命令返回非零结果，TERMINAL 出现失败提示，并在事件队列置顶“需要注意”。
5. **T4**：用户点击失败项，检查器显示 `bash` 调用结果摘要，点击“轨迹”打开原始调用。
6. **T5**：Agent 继续工作，用户返回工作流。真实交付报告存在且可访问时，DEPOT 新增报告条目。
7. **T6**：完成后，状态带只显示实际结束的任务与已记录数据，用户可进入历史检查。不会因为“所有工具成功”就自动宣称整个目标达成。

### 11.2 场景 B：单 Agent 普通聊天

没有 Subagent 也没有显式 Workflow 时仍可使用。地图只展示 HQ、目前使用过的设施、最近工具行动和轮次状态；不填充无意义角色。没有执行记录时展示“这里暂时没有行动，开始任务后会出现实时地图”。

### 11.3 场景 C：用户离线后重新打开

历史事件先被按可信序列还原；尚未加载的前缀显示“部分历史未加载”，不能拿当前已加载尾部推断全程调用次数。网络/Host 重连中显示“状态未知或正在同步”，待实时投影恢复后再呈现当前动作；不会把未知状态画成失败或成功。

### 11.4 场景 D：Workflow 脚本扇出

当存在真实工作流 `phase / member` 数据时，工作流地图增加阶段条和成员分组；没有明确拓扑关系就只显示并发分支，不编造 DAG。多阶段完成遵循已记录成员结算情况，不能根据主 Agent 的临时回复推断所有子工作完成。

# 12. 空态、异常、边界和可信度要求

### 12.1 必须覆盖的状态

- 无 Session：只有启动介绍、样例图与提示；样例必须明确标注 DEMO，不可伪装当前执行。
- 新 Session / 尚无工具：HQ 处于 Idle，世界不空白也不虚假繁忙。
- 仅有主 Agent：保持布局平衡，无 Subagent 建筑也能正常展示。
- 同时 10+ 工具调用：设施活动数聚合、异常单独显示，不强制每个调用生成角色。
- 外部 Subagent：显示身份/关联和可证实结果，内部工具与精确时长未知时不猜测。
- 审批待决：显式标记及跳转，不在画面中自动批准或拒绝。
- 工具无开始事件只有结算记录：允许以“历史已结算”恢复，不补造动画时刻。
- 历史有缺页：呈现数据覆盖范围，不把“部分历史”等同“完整任务”。
- 会话切换：场景与数据严格隔离，不把前一 Session 的角色留在新 Session。
- 插件卸载、重连、窗口隐藏：释放动画和订阅，布局偏好仍可安全恢复。

### 12.2 不确定性语言

“已完成”仅用于真实结算，“可能正在运行”不能替代准确运行事实，“未知”表示缺少证据，“未加载”表示历史分页缺口，“等待审批”需要实际审批状态依据。“尚无可见事件”不等于 Agent 没有行动。

### 12.3 隐私与内容安全

场景默认只显示工具名、短标签和状态，不自动渲染 Shell 输出中的 token、密钥、文件正文或私人路径；详情沿用 dsh 现有脱敏和权限策略。任何来自工具结果的文本只作为文本而非 HTML / 可执行字符解释。离线打包不向 ascii.rest 服务器请求运行时模块或字体；第三方依赖需在发行产物中附带 MIT 通知。

# 13. 体验规范、无障碍与性能预算

### 13.1 视觉系统

**主风格：** 深色终端优先、兼容浅色主题；背景和静止装饰弱对比，状态、选中和异常高对比。色彩作为增强而不是唯一状态手段：忙碌同时有 `RUN`，成功有 `OK`，失败有 `ERR`，未知有 `?`。

**字符设计原则：** 稳定等宽；角色/设施尽量半角；中文标签放在 HTML 层；移动长度短、速率慢；闪烁不超过必要阈值，不依赖突然全屏效果；对外部任务和未加载状态用不同图形语义。

**声音：** MVP 不提供音效。后续如要添加，仅在用户明确开启后触发，且不用于提醒敏感内容。

### 13.2 可访问性

工作流关键状态与事件必须拥有与 ASCII 画面等价的文本树，支持 Tab/Enter/Escape 操作和焦点恢复。鼠标悬停不是唯一交互。尊重系统减少动态效果并提供视图内静态模式；动画暂停不影响实时状态更新。工具提示具有可读名称，防止屏幕阅读器逐字符朗读场景。

### 13.3 性能与稳定性目标（待实测定标）

| 维度 | 首版目标（设计指标，不是测量结果） |
| --- | --- |
| 场景帧率 | 日常 12–15 fps；转场短时不超过 24 fps；Idle 可静帧 |
| 隐藏 Tab | 装饰性动画完全停止，关键数据可在重新激活时同步 |
| 事件规模 | 在 1000+ 已加载事件的历史会话中可导航，不因动画逐条重播而卡顿 |
| 多 Agent | 至少 8 个可见 Agent、16 项并行动作时可读且交互正常 |
| 可用性 | 从原有界面进入工作流或返回轨迹不应中断会话执行 |
| 帧预算 | 动画活跃期间的渲染 P95 目标低于 50ms/帧（验证条件另定） |
| 失败降级 | ASCII 渲染异常时退化为静态事件/状态列表，不丢信息 |

测试至少覆盖 Windows 与 macOS 桌面、深/浅主题、缩放、多窗口宽度、30 分钟持续观察、重连、历史分页与高密度工具调用。

# 14. 迭代路线、里程碑与范围控制

### Phase 0：风险验证原型（Spike）

完成一个真实 dsh 的第三 Tab，接收录制和实时会话事件；绘制 2–3 个 Agent、3 类建筑、工具成功/失败及节点点击；分别验证 ascii.rest 单 piece 方案和纯 DOM/Canvas 备选方案的渲染连续性。

**退出条件：** 真实工具事件驱动而非预设演示；历史和实时结果一致；Tab 切换不断流/不泄露订阅；运行时不依赖第三方网络；异常可点击定位。

### Phase 1：MVP（观测版）

交付第 08 章 P0-01 至 P0-13。首版使用一套基本 ASCII 建筑，允许通过项目文件定制世界文案和装饰强调色；保留一个主画面、必要工具详情、可靠的 Session 隔离与异常降级。暂不制作可视化设定编辑器、音效、复杂回放或成长系统。

### Phase 2：V1（可复盘版）

增加时间游标/回放、显式 Workflow 阶段分组、成果仓库、战报、焦点模式，以及在既有授权下的操作入口。

### Phase 3：V2（可玩扩展版）

角色和世界主题、脱敏分享、远征档案、收藏复盘，视用户真实使用结果决定是否继续投资。

### 14.1 严格避免的范围蔓延

不做第二套 Agent 调度器；不做“将 Agent 移到一个建筑就修改其工具”的功能；不做自定义权限模型；不做不受限制的动态插件代码执行；不承诺实时远程子任务内部可见；不为了好看而增加 Agent 调用。

# 15. 成功指标与验证方案

### 15.1 核心指标

| 指标 | 定义 | 目标方向 |
| --- | --- | --- |
| 任务态识别时间 | 给定会话，找到正在工作的 Agent 所需时间 | 比原有分散查找更短 |
| 错误定位时间 | 从发现失败到打开正确 tool call 详情的时间 | 显著缩短 |
| 可追溯率 | 世界中的行动是否能定位到真实源记录 | 100% 对可点击行动成立 |
| 错误语义率 | 把未确认、外部或未加载事实误判成已完成的比例 | 目标为 0 |
| Tab 二次主动使用率 | 用户首次体验后在真实复杂任务中再次主动打开 | 相比演示流量更有价值 |
| 动效干扰率 | 用户认为动画遮挡判断、需要关掉动效的比例 | 越低越好 |

### 15.2 对照验证实验

选择至少三类任务：单 Agent 文件修改、多个 Subagent 并行审查、包含失败/重试的 Workflow。让用户分别使用原生 Chat/Trajectory 与新增工作流视图完成同样的观察任务。记录任务态识别、异常定位、点击路径与误判情况；主观“好玩”评分独立记录，**不能抵销事实误读**。

**MVP Go / No-Go 建议**：所有可点击行动都有来源；不得产生虚构的 Agent/失败/完成；用户定位关键异常的中位耗时优于基线；ASCII 帧率和窗口切换通过稳定性测试。未达到时先降动效或优化信息架构，而不是加新玩法。

# 16. 风险清单与决策记录

| 风险 | 严重度 | 处理策略 |
| --- | --- | --- |
| “像素游戏”预期与 ASCII 实际风格不符 | 中 | 明确产品叫“ASCII 基地”，首版用字符而非像素精灵 |
| 动画掩盖失败/审批 | 高 | 状态层优先，关键事件常驻，默认弱动效 |
| 真实 Session 事件不包含全部业务意图 | 高 | 只绘制有证据的事实，显式标识未知 |
| 外部 Subagent 缺少可打开子会话 | 高 | 远程占位，禁用内部轨迹操作 |
| ascii.rest piece 频繁重启造成跳帧 | 中高 | 自有场景状态、稳定 renderer、Spike 测试 |
| 大型会话导致重绘成本高 | 高 | 活动动作聚合、事件虚拟化、状态增量更新 |
| 工具输出泄露敏感内容 | 高 | 默认摘要、无自动复制、原生权限与脱敏 |
| 新 Tab 与原生视图偏好冲突 | 中 | 保持 Chat fallback，按现有机制保存选择 |
| DSH API/插件接口仍处于预稳定期 | 中高 | 版本锁定、选用现有扩展点、建立兼容测试 |
| 游戏化鼓励无效 token 消耗 | 中 | 不把调用次数/成本当积分或能力提升 |

### 16.1 已确定的产品决策

- 第三个 Tab 的名称是「工作流」，内部标题用 Agentarium。
- 默认体验是只读的实时观测，而不是可视化编辑流程。
- Agent 和工具的显示必须可追溯到原始会话事实。
- 不依赖外部图片素材或在线加载第三方动画。
- 以 ASCII 作为品牌风格，但渲染层可替换。
- P0 不改变既有 Agent Runtime 的工作行为。

### 16.2 尚需原型验证的问题

1. 真实 dsh 客户端事件窗口对“工具开始/结算/嵌套调用/子 Agent”是否覆盖足够完整？哪些字段需由已有 Client 模型补充？
2. 一个稳定 ascii.rest 场景如何在连续事件到来时避免重启和状态错位？如果必须重建 piece，是否选择自定义 renderer？
3. 用户更喜欢“角色在建筑之间移动”还是“角色固定在岗位上，活动以灯光提示”？以错误定位效率作为优先判据。
4. 哪些工具结果能可靠识别为“产物”？未识别的仅作为记录，不进入成果仓库。
5. 进入回放后用户会不会误以为 Agent 真暂停？需要怎样的模式提示？
6. 第三 Tab 在小窗口和 dsh 右 Sidebar 同时打开时的最低可用尺寸是多少？

# 17. 给开发团队的最小实现边界（非详细设计）

### 17.1 dsh 插件入口

现有 `ui-chat` 使用 `ctx.slots.register({ name: 'conversation.view', id: 'chat', order: 0, ... })`，`ui-trajectory` 使用相同 Slot、`id: 'trajectory'`、`order: 10`。建议第三方 Client 插件遵循 `ui-trajectory` 的形式注册新 view，命名 `agentarium`、顺序 `20`，加载/卸载由 Cordis effect 生命周期控制。

**不应**通过硬改 Electron 主进程、覆盖原始 Chat 组件或注册右侧资源 Tab 解决入口问题。可复用 `ui-conversation`、`ui-session` 的现有事件源和会话作用域模型。外部包安装与配置遵循 dsh Profile/Bundles 的插件管理约定。

### 17.2 模块职责（概念分层）

| 模块 | 责任 |
| --- | --- |
| dsh View Plugin | 注册 Tab、收集 Session scope 与基本导航能力 |
| Evidence Adapter | 把已确认的事件转为稳定的业务事实与标识 |
| World Projector | 构建 Agent/Facility/Action 的世界状态及回放投影 |
| Animation Director | 根据状态变化生成非权威视觉指令（时长、移动、效果） |
| ASCII Renderer | 用 ascii.rest / 自绘网格渲染字符场景 |
| Interaction Layer | 事件列表、检查器、键盘导航、原生跳转 |
| Replay Controller（P1） | 基于真实事件序列维护历史游标，不操纵后台执行 |

这不是要求建立七个 npm 包；它们首先是**明确的职责边界**。P0 可以实现为一个插件工程内部的模块。

### 17.3 组件使用示意

```ts
// 静态概念示意：ascii.rest 可以用字符网格画一个基地。
import { piece } from 'ascii.rest/kit'

const base = piece({
  name: 'agent-base', cols: 48, rows: 12, fps: 12,
}, (t, s) => {
  s.write(2, 2, '+--- ARCHIVE ---+')
  s.write(25, 2, '+-- TERMINAL --+')
  s.write(6, 7, `A1${Math.floor(t * 2) % 2 ? '.' : ' '}`)
})

// 真正的 Agent 状态、时间轴和交互逻辑应来自独立 World Model。
```

这段代码只证明字符绘制形式，**不是**完整动态 Agent 实现；真实插件还需要数据映射、稳定角色身份、回放、性能、安全与响应式设计。

# 18. 交付标准与验收清单

**必须全部通过，才能称为可交付 MVP：**

- [ ] 安装后确实出现 `[对话][轨迹][工作流]`；顺序正确，原有默认与历史偏好不被破坏。
- [ ] 不修改 Electron 源码即可在 Desktop Web Client 运行；普通 Web 模式也可正确打开。
- [ ] 主 Agent、可见子 Agent、工具开始/结算、失败/取消等基于真实事件，不依赖预演数据。
- [ ] 每个可点击工具事件可定位回其真实记录，不显示不存在的 callId/子会话。
- [ ] 没有显式 Workflow 的 Session 也正常展示，不伪造阶段或百分比。
- [ ] 外部 Subagent 未知状态、历史分页不足、连接失效均有显式提示。
- [ ] 动画关闭/减少动效时信息完全可用；Tab 隐藏后无持续装饰绘制。
- [ ] 错误与审批视觉优先于装饰动画，用户能快速定位源详情。
- [ ] 默认不渲染敏感工具正文，不从 ascii.rest CDN 拉取运行时资源。
- [ ] ASCII 渲染失败可降级到事件列表而不影响 dsh 任务执行。
- [ ] 1000+ 历史事件和 8 个可见 Agent 的压力场景通过预定基准测试。
- [ ] 打包产物包含依赖许可信息与可重复构建的版本锁定。
- [ ] 项目世界设定按 [WORLD-SETTING.md](WORLD-SETTING.md) 验收，模型修改只影响表现，不改变真实执行事实。
